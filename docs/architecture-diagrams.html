01 — 設計書 §21.2 / 規約 §2.2

レイヤと依存方向

依存は上から下への一方向だけです。TerminalCore は誰も参照せず、 UI・外部プロセス・ネットワークを知りません。ビルドシステムは逆向きの依存を検出しないので、 この向きは目視で守るしかない、というのが規約 §2.2 の趣旨です。

02 — 設計書 §20.1 / §21.2 / §21.4 / Package.swift

モジュール構成（SwiftPM ターゲット）

現在のターゲットは TerminalCore と Adapters の 2 つだけです。 完成形では macOS ホストと iOS クライアントで別のアプリを作りますが、 ドメインと Feature は共有し、renderer と通信手段だけが分かれます。 設計書 §21.5 で「モバイルの renderer は macOS と共通であることを要求しない」と確定しているため、 プラットフォーム差はこの 2 か所に閉じ込めるのが構成上の要点です。

03 — 規約 §2.1 / §2.2 / 設計書 §12.1 / §21.5

境界 protocol と依存関係の逆転

外部世界（tmux・git・libghostty・SQLite・SSH）に触れる型は、protocol を TerminalCore 側に宣言し、実装体を Adapters 側に置きます。 こうすると依存の矢印は内向きのまま、呼び出しは外向きにできます。 libghostty をこの境界の外へ漏らさないことが、規約が明示的に禁止している唯一の実装リークです。

04 — 設計書 §2 / §3 / §9 / §10 / §14 / §22

ドメインモデル

TerminalCore が持つ値の関係です。実線は所有、破線は導出を表します。 この図で一番効くのは右側の枠で、Diff snapshot・Consultation・Evidence は worktree の生存に依存しません。 worktree を削除しても当時の質問対象やレビュー内容を参照できる、というのが設計書の要求だからです。

05 — 設計書 §12.1 / §12.2 / §12.3

Agent 状態の正規化

このプロダクトで唯一すでに実装されている経路です。tmux の出力を値型に写し、Adapter が Agent 固有の情報を 共通状態へ正規化し、純粋関数が worktree の代表状態を 1 つ決めます。 状態を確定できないときに working / idle へ丸めないことが、この経路の設計上の要です。

06 — 設計書 §18 / §20.1 / §21.4 / §21.6

プロセス配置とリモート

コードがどのプロセスに載るかの図です。アプリは 1 プロセスに閉じず、tmux サーバ・git・ripgrep・Agent 本体は すべて別プロセスとして外にあります。アプリを落としても tmux と Agent は生き続けるのがこの配置の眼目で、 だからこそ Host Core を常駐 daemon にしない判断が成立します。

07 — 設計書 §15 / §19.1 / §22

永続化レイアウト

保存は 2 系統に分かれます。実体（画像・コード snapshot）はファイルシステム、metadata だけが SQLite。 SQLite に画像を入れないのは容量管理と cleanup を Storage 画面で一本化するためです。 モバイルの UI 状態だけは host の DB へ同期しません。端末ごとに独立という §19.1 の原則が優先します。

08 — 設計書 §3.1〜§3.5

worktree ライフサイクル

構成図の外側にある、実装の前提となる時間軸です。 worktree を作るのは Terminal ではなく Agentで、Terminal は検出・表示・Active 管理だけを担当します。 命名や配置の規則が Project 固有だからで、この責務分割がそのまま GitAdapter を読み取り専用に保つ根拠になります。

10 — この資料の運用

更新ルールと追加提案

この資料は docs/architecture.md の従属物です。設計書が正で、図が誤っていたら図を直します。 /decide で項目を確定へ昇格させたときは、本文・§25/§31・付録 A/B に加えてこの資料の枠線色とステータス表も更新してください。 逆に、この図で提案しているモジュール名（点線の要素）は設計書には存在しないので、実装に着手するときに設計書側へ昇格させるか、図から落とすかを決めます。

提案 1 — ターゲット依存図を CI で検証する

図 2 は手描きなので、実装が進むと必ず現物とずれます。swift package dump-package の JSON から ターゲットと依存を取り出し、この HTML に埋めた宣言（data-* 属性など）と突き合わせて差分があれば CI を落とす、という小さなチェックが作れます。 規約 §2.2 の「逆向きの依存はビルドシステムが検出しない」という穴を、そのまま埋められます。

提案 2 — Gate 進捗ダッシュボードを別資料にする

設計書 §24 の Gate 1〜5 と、Gate 1 で「本実装後に計測」と送られた 4 項目（長時間稼働、複数 surface のメモリ、外部ディスプレイ、vttest 相当）は、 いま README とスパイクに散っています。構成図とは別に、Gate の状態・実測値・残課題を 1 枚にした資料があると、 「次に何を作るか」が構成図から直接引けます。

提案 3 — 用語の対応表を持つ

Terminal 共通の Agent 状態（working / needsAttention …）と、Agent Skills 側の内部状態 （IMPLEMENT / HUMAN_REQUIRED …）は設計書 §30 で明確に別物と決まっていますが、名前が似ていて混同しやすい箇所です。 両者の対応表を図として持っておくと、Adapter 実装時に「Terminal 側が phase を発明しない」という §32 の原則を守りやすくなります。

提案 4 — 決定の経緯を ADR に分ける

設計書は「現在の仕様」を書く場所で、なぜ他の案を捨てたかは §21.6 の表に圧縮されています。 libghostty の iOS 除外や Mosh 回避のように、後から必ず「なぜ？」と聞かれる判断は、 日付と根拠つきの ADR に切り出すと設計書本文を現在形に保てます。コミットログ＝Why の規約とも整合します。
