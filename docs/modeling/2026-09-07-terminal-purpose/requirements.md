# Terminalの利用目的と受け入れ条件

2026-09-07のユーザーとの対話で合意した要件。現行仕様の正本は `../../architecture.md`、
フェーズ進行は `../../roadmap.md`、実装タスクはGitHub Issuesとする。本書は目的確認の記録である。

## 目的と利用者

単一の開発者が3プロジェクト、各2〜3タスクを並行して扱う。各タスクの別paneに
Claude CodeやCodexを複数起動する。第一の課題は各セッションの目的を思い出す時間、
第二の課題は判断待ちの見落とし。Agent内部のsubagent一覧は今回の対象ではない。

人間は要件・設計を質問に答えながら確認し、PRレビューを行う。ハーネスが進行を制御し、
アプリは観測・表示・通知・対象への移動を担当する。

## ユースケースと受け入れ条件

| ユースケース | 優先度 | 成功条件 |
| --- | --- | --- |
| 全セッションの目的を確認する | Must | 独立Overviewで全Project/Task/Agent paneをタスク切替なしに閲覧できる |
| 現在地を思い出す | Must | 「ログイン不具合を修正する｜設計相談中」程度の概要と状態アイコンを確認できる |
| 判断待ちへ戻る | Must | 別paneを含む判断待ちを把握し、対象paneへ直接移動できる |
| ハーネスなしで使う | Must | 概要を手入力でき、通常Terminalとして動く。取得できない現在地は推測しない |
| タスク完了を知る | Must | ハーネスの明示した完了を通知し、paneの応答終了では代用しない |
| 外出中に通知を受ける | Must | Macアプリ起動中、ロック済みiPhoneでアプリを開かず判断待ち・完了通知を受ける |
| 外出中に介入する | Should | 通知から回答、プロンプト送信、新規タスク開始へ進める |
| Diffを別窓で確認する | Should | タスクと比較元を指定する。組み込み別窓と外部ツール連携のどちらも許容する |
| Gitツリーを見る | Could | 表示方法は後続で検討する |

Mustは中核要件の優先度であり、既存P2の変更指示ではない。導入順はロードマップに従う。

## 制約と未確定事項

編集はvi・外部IDEに委譲する。ハーネス連携は任意であり、Terminal専用APIをハーネス実行の
前提にしない。連携なしではタスク完了を推測して通知しない。Unknownは独立表示する。

通知中継はopt-inかつ最小payloadとし、コードやTerminal出力を送らない。
概要連携の形式・優先順位・セッションの寿命・メインpaneの登録方法、完了の再実行時解除、
重複/古いイベント、通信復帰、消失したpaneへの導線は実装前に具体化する。
通知遅延・検出漏れの数値目標は未確定。実測結果と利用上の許容条件を合わせて判断する。

## 設計・進め方の評価

worktree/tmuxによる分離とハーネスとの責務分離は目的に合う。一方、タブ代表状態だけでは
全paneの目的を把握できないため、独立Overviewを中核へ加えた。
pane応答終了とタスク完了の混同を避ける契約を明示した。
モバイルはTerminal完成より通知の成立を先にする。保留課題の全消化をフェーズ完了条件にせず、
実際に使える体験で終了判定する。P2までのタスクは維持する。
